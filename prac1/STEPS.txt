Aim: run a Spark job, see data skew in the Spark UI, and fix it with salting.

IN SIMPLE WORDS
---------------
   - Shuffle means Spark moves rows between partitions so that rows with the same key sit together. groupBy and join cause a shuffle. It is the slowest part of a job.
   - Data skew means one key has far more rows than the others. Here key 0 has 90% of 5 million rows. One task gets almost all the work while the other tasks finish quickly and wait.
   - Salting is the fix. Add a random number (the salt, 0 to 7) to each row. Key 0 becomes eight smaller groups: 0+salt 0, 0+salt 1, and so on. Now eight tasks share the work.
   - Salting needs two steps: first count per (key, salt), then add those small counts back per key.

Think of one billing counter with 900 people and seven counters with 15 each. Salting sends the 900 people to all eight counters.

EASY CODE (SKEW.PY)
-------------------

      import time
      from pyspark.sql import SparkSession
      from pyspark.sql.functions import col, when, rand, sum as _sum
      
      # Start Spark on 4 cores, with 8 shuffle partitions
      spark = (SparkSession.builder.appName("SkewDemo").master("local[4]")
               .config("spark.sql.shuffle.partitions", "8")
               .getOrCreate())
      spark.sparkContext.setLogLevel("ERROR")
      
      # 5 million rows. 90% get key 0, the rest get keys 1 to 999
      n = 5_000_000
      df = spark.range(n).withColumn(
          "key", when(col("id") < n * 0.9, 0).otherwise(col("id") % 999 + 1))
      
      print("PROBLEM: one key has 90% of the rows")
      df.groupBy("key").count().orderBy(col("count").desc()).show(5)
      
      # FIX step 1: add a random salt from 0 to 7
      salted = df.withColumn("salt", (rand() * 8).cast("int"))
      
      # FIX step 2: count per (key, salt) -> key 0 is now 8 small groups
      part = salted.groupBy("key", "salt").count()
      print("After salting: key 0 is split into 8 small groups")
      part.filter(col("key") == 0).orderBy("salt").show()
      
      # FIX step 3: add the small counts back together per key
      final = (part.groupBy("key").agg(_sum("count").alias("count"))
               .orderBy(col("count").desc()))
      print("FINAL: same answer as before")
      final.show(5)
      
      print("Open the Spark UI: http://localhost:4040")
      time.sleep(120)   # keeps the Spark UI alive for 2 minutes
      spark.stop()

WHAT CHANGED FROM YOUR JOURNAL CODE
-----------------------------------
   - The long java_flags block is removed. Current PySpark adds those Java 17 flags by itself.
   - Your journal joins key and salt into one text column (concat_ws). Grouping by the two columns key and salt does the same job with less code.

One point for viva: salting matters most in joins and heavy aggregations. For a plain count, Spark already does a small count inside each partition before the shuffle, so the skew you see in the UI is mild.
